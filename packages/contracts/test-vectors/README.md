# Protocol conformance vectors

What every file here is, how to regenerate it, and the three rules that govern
all of them.

The design record is
[`specs/002-native-foundation-ios/contracts/conformance-vectors.md`](../../../specs/002-native-foundation-ios/contracts/conformance-vectors.md).
The protocol they pin is [`docs/protocol/`](../../../docs/protocol/).

## The three rules

1. **Vectors come out of production code paths.** A generator that
   reimplements the algorithm proves the generator, not the implementation.
   Where a generator has no production path to call — the MPAK writer is
   server-side and is deliberately not imported — the file records container
   bytes and asserts the production **reader**, and says so.
2. **Verification is a separate program from generation.** The generators live
   in `../scripts/`, the verifiers in `../src/__tests__/`, and a verifier never
   imports a builder. The committed JSON is the verifier's input and is never
   regenerated by it. A generator-only gate passes when the implementation and
   the generator drift together; a verifier-only gate passes when a committed
   vector is stale in a way the implementation happens to still satisfy. Both
   halves are required.
3. **A change to a covered format updates the chapter and the vectors in the
   same change.** `vectors:check` is what makes that a red build rather than a
   review note, and `protocol-chapters.test.ts` is what makes the chapter's own
   fact tables fail when a constant moves under them (FR-008).

## Commands

```bash
pnpm --filter @memry/contracts vectors:check       # CI runs THIS; it writes nothing
pnpm --filter @memry/contracts vectors:generate    # rewrites the committed files
pnpm --filter @memry/contracts test                # the eleven verifiers
pnpm --filter @memry/contracts vectors:digest      # the FR-008 chapter digest
```

`vectors:check` regenerates every class into a temporary directory and diffs
against the committed files **without writing**, so an accidental run in a dirty
tree cannot mask a drift by overwriting the thing it was meant to compare
against. It catches a constant change, a `pako` upgrade, a `cborg` upgrade and a
field-order edit.

One class regenerates alone —
`npx tsx scripts/gen-protocol-vectors.ts cbor-canonical` — which is what makes a
one-class change reviewable.

`crypto-vectors.json` is **frozen**: it is byte-for-byte as committed and no
change in this feature touches it. Three suites consume it and none of them
should see a diff. Every new case landed in a new file.

`deterministic-provider.ts` is not a vector file. It is the shared
`SyncPushCryptoProvider` that injects a fixed file key and fixed nonces so a
production writer produces reproducible bytes.

### `note-blocks.json` compares documents, not update bytes

The class carries two expectations per case: `expectedBlocks`, the block list a
shell renders, and `expectedCanonical`, the document rendered through the
**canonical fragment serialisation** (`../scripts/fragment-canonical.ts` and
`crates/memry-core/src/crdt/canonical.rs`).

The second exists because Y update bytes **cannot** be compared across ports. An
update encodes `clientID` and per-client clocks, and struct ordering, origin ids
and run-length packing are free choices an implementation may make differently
while still converging. Two different updates that converge are both correct, so
a byte comparison would fail on correct ports and catch nothing extra. The
canonical form carries node names, nesting, sorted attributes and text, and
nothing about how the document was built.

Its corpus is authored through **BlockNote itself**
(`@memry/editor-schema/conformance-ydoc`, which calls the same
`blocksToYXmlFragment` desktop main calls), so the bytes are the bytes a real
note carries rather than what someone believed y-prosemirror writes. Block ids
are assigned deterministically rather than left to BlockNote's v4 UUIDs: an
unpinned id makes the class non-reproducible and would silently exempt it from
`vectors:check`.

### `block-edit.json` is the write direction, and it runs some cases inverted

Each case is a base document, one operation, and the document the operation
must leave behind. A port applies the operation and re-renders through the same
canonical form; it never compares the update it emitted, for the reason above.

Both documents are authored through BlockNote, which makes the assertion **"the
writer produces the document BlockNote would have produced"**. That is what
chapter 12 §12.5.0 demands rather than merely suggests: y-prosemirror answers a
node its schema cannot construct by **deleting the element**, silently — the
update applies, the document encodes, `extract_text` may still return the text,
and the next desktop to open the note renders it without the block. A writer
held only to its own idea of the shape cannot catch that.

There is no TypeScript verifier for the operations themselves, because there is
no TypeScript writer: node construction lives in Rust by design. The TypeScript
half proves the file is a sound contract — that both canonical strings really
are what those documents render to, that every operation names a block its base
holds, that a result differs from its base, and that every base and every result
has exactly one top-level `blockGroup`.

A case carrying `pending` **fails against the writer as it stands** and is
asserted to fail, so fixing the writer turns it red and forces the flag's
removal. Remove the flag, never the case — the same convention `ROUNDTRIP_CASES`
uses. Four cases are pending today, and each one is a real defect the class
found rather than a known-bad input:

- `insert_paragraph` writes a bare `paragraph` where BlockNote writes one
  carrying `backgroundColor`, `textAlignment` and `textColor` at their declared
  defaults. Both render the same, so nothing is lost today, but they are not
  the same document.
- the append path adds a `blockContainer` **beside** the existing `blockGroup`
  as a second top-level child, which is the §12.5.0 silent-deletion trap.
- `SetProp` stores every value as a string, so `checked` lands as `"true"`
  where BlockNote writes the boolean `true`. Unticking stores `"false"`, and a
  non-empty string is truthy — a box cleared on one client reads as ticked
  anywhere that tests the prop for truth. Latent only because no shell calls
  `Notes.editBlock` yet.
- `level` lands as `"5"` where BlockNote writes `5`.

### `attachment-manifest.json` pins two things that fail silently

Chapter 14 §14.4's manifest is the only thing that names an attachment — chunks
in R2 are opaque ciphertext addressed by hash — so its signature is what stops
a server-side swap pointing a note's picture at somebody else's bytes. The Rust
core reimplements that signing rather than sharing it, because there is no
place both ports can call: the core is a standalone library a Swift shell
links. This class is what holds the two together, and the Rust harness asserts
the **envelope bytes** match, not merely that each port can read itself.

The first trap is the signature payload's order. It is canonical CBOR, and
canonical order is **not** the `CBOR_FIELD_ORDER.ATTACHMENT_MANIFEST` listing
order: the encoder sorts by key length and then bytewise, so the signed order
is `keyNonce`, `manifestNonce`, `encryptedFileKey`, `encryptedManifest`. A port
signing the listing order produces perfectly valid CBOR and a signature nobody
else accepts.

The second is that the signature covers the four envelope fields and **not the
manifest body**. The body crosses as `JSON.stringify` output, so a port that
emitted the same fields in a different order would produce a manifest every
other port still parses — nothing fails, and the two drift silently. The class
therefore records `manifestJson` as its own field and both harnesses assert it
byte for byte.

One case carries a writer that chose a 2-byte chunk size, because §14.9 makes
`CHUNK_SIZE` a desktop constant rather than a contract constant: a reader sizes
every chunk from `chunks[j].size`. A port that hardcoded 8 MiB reads that file
wrong, and the failure would be a truncated download rather than an error.

Verification order is behaviour rather than bytes, so both harnesses swap each
signed field in turn and require a **signature refusal** — not a decrypt
failure, which is what a reader that unwrapped first would report.

The read verifier asserts coverage **against `registry-manifest.json`** rather
than against a hand-counted list, so a type nobody wrote a case for is a failing
test. That is what makes "a new block type is not done until it has a case"
enforceable. It is also the gap that let two real defects ship: `divider` was
dropped before it left the core, and inline colour values never crossed at all.
Both passed the only test that existed, which compared the block walk against
the text walk of the _same_ port — two readings that agree with each other
whether or not either is right.

## Determinism

The production crypto path draws a fresh random nonce per operation and a fresh
random file key per item. A vector cannot contain a random value and also be
reproducible, so **every generator injects its entropy**. Two techniques, and no
third:

- **D1 — call the production function with injected material.** Preferred
  wherever the function already takes it as a parameter: `encodeCbor`,
  `compressPayload`, `mergeFields`, `parsePack` and the KDF calls are all pure
  given their inputs.
- **D2 — stub the randomness seam, not the algorithm.** For a writer that
  generates its own nonce, the generator passes `deterministicProvider()`, whose
  `generateFileKey`, `encrypt` and `wrapFileKey` return fixed bytes and whose
  every other method is real libsodium. The provider seam exists in production,
  so this is still a production code path with a test-supplied entropy source.

Recording a generated nonce into the file as an input was considered and
rejected: it makes a file reproducible by the verifier but not by the generator,
which is exactly the carve-out that would exempt the most important classes from
the `vectors:check` gate.

Yjs documents are built with a **pinned `clientID`** for the same reason: an
unpinned document encodes a random id into every update.

Fixed material, shared across generators so a reader can correlate two files, is
in `deterministic-provider.ts` under `FIXED`.

## Three places this differs from the design record, and why

The design record was written before the code was; these are the points where
following it literally would have broken something.

1. **The record-envelope and CRDT-update vectors are generated from
   `@memry/sync-client`, not from desktop.** §5 names desktop's
   `encryptItemForPush`. `apps/desktop/src/main/sync/encrypt.ts` reaches
   `crypto/primitives.ts` → `memory-lock.ts` → `lib/logger.ts` →
   `electron-log`, so importing it into a `packages/contracts` script pulls
   Electron into a package that must not depend on an app — the boundary §10 of
   the same document refuses to breach for the pack writer.
   **The parity assertion is not lost.** It moves to
   `apps/desktop/src/main/sync/vector-parity.test.ts`, which runs in
   `pnpm test:desktop` where desktop's modules are importable, and asserts
   desktop's writers produce byte-identical output to these files. Both
   TypeScript writers are pinned to one committed artefact, which is what §5
   exists to achieve. The two vault-name cases live there for the same reason.
2. **`bip39-unlock.json` is built by `gen-protocol-vectors.ts`, not by
   `gen-crypto-vectors.ts`.** §4 names the latter. The composite entry point is
   the one `vectors:check` drives, so building it there puts the new file under
   the FR-008 gate instead of leaving it regenerable only by hand.
   `crypto-vectors.json` is untouched either way.
3. **280 cases, not 275.** The five extra are deliberate, and each earns its
   place:

   | Delta | Where                           | Why                                                                                                                                                                                                                                                                    |
   | ----: | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   |    +1 | the §14 totals table itself     | Its primitives row reads 20; the groups in `crypto-vectors.json` sum to 21 (2 + 2 + 1 + 7 + 3 + 1 + 2 + 2 + 1). The plan's own arithmetic was one short                                                                                                                |
   |    +1 | `bip39-unlock.json`             | The `deviceId` derivation is a named case rather than a verifier-only assertion, so a second implementation can fail it directly                                                                                                                                       |
   |    +2 | `field-merge.json`              | `totals-equal-local-offline-zero-tick` pins that the `_offline` tie-break is a KEY-PRESENCE test — `{_offline: 0}` still wins — which no other case reaches; `float-accumulation` pins that `0.1 + 0.2` and `0.3` differ, the other half of the number-formatting case |
   |    +1 | `markdown-roundtrip/cases.json` | A sixth out-of-band case carrying a **foreign root no client knows**. Without it the class only proves that roots someone remembered to list survive, which is strictly weaker than the claim FR-033 makes                                                             |

## Two things a reviewer should check before trusting a change here

- **Did the chapter change too?** A vector diff with no `docs/protocol/` diff is
  either a bug in the generator or a format change that skipped its
  specification. Both are rule 3 failures.
- **Does the negative control still fail?** Several verifiers assert that a
  wrong implementation fails — that pushing a projection back loses an unknown
  key, that rebuilding a Y.Doc through named accessors drops a foreign root,
  that the two linking MAC families do not reproduce each other. Those
  assertions are what keep the positive ones from being vacuous, and a change
  that quietly makes one pass has removed a test without deleting it.
