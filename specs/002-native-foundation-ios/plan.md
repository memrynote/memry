## Summary

Write the vault protocol down, prove a second implementation against it, and
ship the first native phone shell over that implementation. Three deliverables
in strict order:

1. **Protocol specification and conformance vectors** in the TypeScript repo:
   `docs/protocol/` chapters derived from the existing code, plus composite
   vectors (signed record envelope, packed CRDT update, MPAK, field-merge
   cases, canonical CBOR, compression framing, markdown round-trip corpus)
   generated by production code paths and verified by the desktop suite.
2. **`crates/memry-core`** (Rust, UniFFI): auth and token lifecycle, libsodium
   crypto, sync engine and outbox, yrs CRDT ownership, SQLite storage with
   FTS5, domain logic for notes, folders, tags, properties, templates,
   journal, tasks, projects (read and assign), reminders, settings, search.
   Proven headless by `crates/memry-cli` against staging with a real desktop
   on the other side before any UI exists.
3. **`apps/ios`** (SwiftUI, iOS 26+): sign in (OTP, Google, Apple), unlock
   (recovery phrase, QR link with SAS), multi-vault, notes with the
   WebView-hosted BlockNote editor over bridge protocol v1, folders, tags,
   search, journal, tasks, reminders, settings sync, read-only kill-switch
   mode, sign-out and revocation, account deletion, TestFlight-ready.

The server changes only additively (Apple identity provider, spec-driven
tests). Vector generation lives in `packages/contracts`, not on the server.
Desktop does not change. `apps/mobile` is frozen; `editor-web` moves out of
it to `packages/editor-web`.

No GoogleSignIn-iOS SDK. No third-party Keychain wrapper. No Rust networking
on device: HTTP and WebSocket come from the shell through foreign traits.

**Storage**: two SQLite databases per vault owned by the core (data plus
index), WAL, hand-rolled `user_version` migrations, FTS5 from `bundled`.
The two-namespace Yjs update log is the body of record; next to it sits
extracted plain text for FTS and previews, and the create-time seed payload
held verbatim until the WebView seeds the document. Files in
`Application Support/<bundle>/vault/<vaultId>/` under
`completeUntilFirstUserAuthentication`, excluded from backup. Secrets in
Keychain, `AfterFirstUnlockThisDeviceOnly`, data-protection keychain, bytes
only. Schema in [data-model.md](./data-model.md).

**Testing**: `cargo test` (unit, vectors via `include_str!`, `insta`
snapshots, `proptest`); Swift Testing for iOS units and on-device
conformance (`@Test(arguments:)` over the same vector file); XCTest only for
the single editor smoke UI test and performance; Vitest on the TypeScript
side verifies every generated vector. Sync-seam tests run against the real
SQLite adapter and, in the CLI round trip, the real staging server.

**Target Platform**: iOS 26+ on every iPhone that runs it; performance
reference device iPhone 15. `memry-cli` on macOS and Linux. Android later
over the same core.

**Project Type**: Rust workspace (`crates/`) plus a Swift app (`apps/ios`)
plus a local Swift package wrapping the XCFramework, inside the existing
pnpm monorepo.

**Performance Goals** (spec SC-004 to SC-007, SC-015, SC-016): under 50 ms
keystroke-to-render on a 50 KB note; write visible cross-device under 5 s;
10,000-item vault browsable within 2 min on Wi-Fi; search p95 under 300 ms
on 10,000 items; bridge flush cadence no faster than 24 ms with envelopes at
or under 256 KB; no per-keystroke FFI call.

**Constraints**: offline-first; durable across process death (outbox and
CRDT state committed before any acknowledgement); startup never gated on the
network; recent-body window first; images lazy and unmetered-first; no
certificate pinning; no background polling loop; batching on both sides of
both boundaries. The interval status poll that learns client policy is
suspended while the app is backgrounded and resumes on foreground, so it is
not a background polling loop.

**Scale/Scope**: solo developer; 77 FRs; 13 subscribed record item types;
33 distinct editor node, inline, and style types the bundle must build.

**Unknowns**: none remaining. Research items R1 to R19 in
[research.md](./research.md) resolved all of them. Residual uncertainties are
listed there in section E with named verification tasks.

## Decision Record Fidelity

Every decision in the decision record is carried unchanged except three
refinements made during Phase 0, all already written back into the record
and the constitution:

| Record said                         | Refined to                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Why                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Core owns "HTTP/WebSocket client"   | Core owns the client logic; the socket is a shell-provided transport seam                                                                                                                                                                                                                                                                                                                                                                                                                              | iOS suspends raw sockets and applies ATS and background transfer only to its own stack (R5)                                                                                                                                                                                                                                                                                                                                        |
| Server unchanged                    | Server gains an additive Apple identity provider                                                                                                                                                                                                                                                                                                                                                                                                                                                       | App Review 4.8 requires an equivalent private-email login when Google is offered (R14)                                                                                                                                                                                                                                                                                                                                             |
| Core stores note bodies as markdown | The Rust core never serialises or parses BlockNote markdown. Both directions run inside the WebView bundle (BlockNote plus `@memry/editor-schema`) over bridge messages: `export-markdown`, which exists, and a new `seed-from-markdown` used on note creation and template application. The core provides `extract_text(doc)`, a plain-text walker over the `prosemirror` `XmlFragment` that keeps headings and list markers and makes no markdown-fidelity claim, feeding FTS `content` and previews | A markdown-to-Y.Doc path in Rust means the whole BlockNote block model in Rust, and a markdown serialiser in Rust means a second grammar to keep byte-identical forever. The bundle already owns both directions correctly. Frontmatter handling lives in the editor surface too: the create-time `content` payload is split by the shared splitter inside the bundle, so the core does no markdown or frontmatter handling at all |

FR-041's byte identity is satisfied **structurally**, not by a Rust markdown
serialiser: the phone never writes vault files. Desktop remains the only
writer of markdown on disk, so a body it wrote and a phone edited returns
through the same desktop serialiser it came from.

| `seed_markdown` held verbatim in `note_bodies` | the create-time `content` payload must survive until the editor surface seeds the document | storing it anywhere else would need a second durable store; the core never interprets the bytes and clears them after the first document update |

Beyond that one column, **the core does no markdown handling and no frontmatter
handling at all**. Both directions, frontmatter split included, live in the editor
bundle.
