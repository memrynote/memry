# Contract: Conformance Vector Set

**Feature**: 002-native-foundation-ios | **Date**: 2026-09-12 | **Spec**: [spec.md](../spec.md)

The design of the vector set required by FR-005 through FR-008. Two vector classes
already exist and ship today; eleven are new. This document says where the files
live, which production code generates each class, how determinism is obtained when
the production path uses random nonces, what the JSON looks like, what the desktop
suite asserts, what the Rust suite asserts, and how many cases each class needs.

Governing constraints:

- **Vectors come out of production code paths.** A generator that reimplements the
  algorithm proves the generator, not the implementation. Where a generator today
  hand-copies a table instead of importing it, that is called out below as a defect
  to fix, not a pattern to follow.
- **The desktop suite must fail when a vector and the implementation disagree**
  (FR-006). Verification is a separate program from generation, and the committed
  JSON is the input to verification, never regenerated by it.
- **The Rust core must reproduce every vector byte for byte before any feature work
  depends on it** (FR-007, SC-001).
- A change to a covered format updates the specification chapter and the affected
  vectors in the same change (FR-008).

## 1. File layout

Everything lives under `packages/contracts/test-vectors/`, which is already the
committed location and is already exported from the package
(`packages/contracts/package.json:74`). File names follow
[plan.md](../plan.md), Project Structure.

```text
packages/contracts/test-vectors/
  crypto-vectors.json          # EXISTS, unchanged. primitives + password-based vault unlock
  bip39-unlock.json            # NEW. recovery phrase to seed to master key, and the verifiers
  record-envelope.json         # NEW. signed record envelope, including vault-name envelopes
  crdt-update.json             # NEW. packed CRDT update envelope
  pack-container.json          # NEW. MPAK container, reader only
  cbor-canonical.json          # NEW. canonical CBOR encodings
  compression.json             # NEW. compression framing
  field-merge.json             # NEW. merge winner, conflict set, clock algebra, offline rebind
  payload-schemas.json         # NEW. one group per subscribed item type, verbatim round trip
  device-linking.json          # NEW. both MACs, SAS, proof, confirm
  text-extract.json            # NEW. Y update bytes to extract_text output
  markdown-roundtrip/          # NEW. corpus exported from editor-schema conformance
    cases.json
    fuzz-families.json
  README.md                    # NEW. what each file is, how to regenerate, the rules above
```

`crypto-vectors.json` stays byte-for-byte as committed, per
[plan.md](../plan.md), Project Structure. **Every new case lands in a new file**,
without exception: the recovery-phrase gap identified in section 3 is closed by
`bip39-unlock.json`, and the two other changes section 3 asks for are verifier-only
assertions that add no case to the committed file. Three test suites already consume
`crypto-vectors.json` and none of them should see a diff from this feature.

Generators, per [plan.md](../plan.md), Project Structure:

```text
packages/contracts/scripts/
  gen-crypto-vectors.ts        # EXISTS, extended with the BIP39 and verifier groups
  gen-protocol-vectors.ts      # NEW. one entry point emitting every composite class
```

`gen-protocol-vectors.ts` takes an optional class filter so a single class can be
regenerated in isolation, and `--check` regenerates into a temporary directory and
diffs against the committed files without writing.

Verifiers live beside the one that exists,
`packages/contracts/src/__tests__/`, one test file per vector file.

Wiring. The existing test is picked up three independent ways and the new ones
inherit all three: the desktop vitest `shared` project includes
`../../packages/contracts/src/**/*.{test,spec}.{ts,tsx}`
(`apps/desktop/config/vitest.config.ts:34`); the root `pnpm test` runs
`turbo run test --filter=@memry/contracts` among others
(`package.json`, the `test` script); and mobile CI runs the file directly
(`.github/workflows/mobile-ci.yml:96`). So a new vector test is in the desktop
suite the moment the file exists, with no wiring change. That satisfies FR-006
without new plumbing.

Two gaps to close while adding files:

1. **There is no npm script for the existing generator.** The only documented
   invocation is a comment: `npx tsx packages/contracts/scripts/gen-crypto-vectors.ts`
   (`packages/contracts/scripts/gen-crypto-vectors.ts:13`). Add
   `"vectors:generate"` and `"vectors:check"` scripts to
   `packages/contracts/package.json`, each running both generators.
2. **FR-008 needs a gate, not a habit.** `vectors:check` regenerates **every** vector
   file into a temp directory and diffs against the committed file, failing on any
   difference. It runs in CI alongside the verifiers. That is the mechanism that makes
   "a format change must update the vectors" a red build rather than a code review
   note. There is no carve-out: every class is reproducible by construction, because
   every generator injects its entropy rather than recording it (section 2).

## 2. Determinism strategy

The production crypto path generates a fresh random nonce per operation
(`apps/desktop/src/main/crypto/encryption.ts:6-16`) and a fresh random file key per
item (`apps/desktop/src/main/crypto/primitives.ts:4-6`). A vector cannot contain a
random value and also be reproducible. Two techniques, and no third:

**D1. Call the production function with injected material.** Preferred wherever the
production function already takes the material as a parameter. `wrapFileKey`,
`deriveKey`, `crypto_kdf_derive_from_key`, `crypto_sign_detached`, `encodeCbor`,
`compressPayload` and `decompressPayload` are all pure given their inputs. The
existing generator uses exactly this: every seed, salt, key and nonce is a hard
coded hex constant and the sodium call is the real one
(`packages/contracts/scripts/gen-crypto-vectors.ts:44-52`, `:130`, `:242-243`).

**D2. Stub the randomness seam, not the algorithm.** For a production function that
generates its own nonce internally, the generator provides a deterministic
`SyncCryptoProvider` whose `generateFileKey` and `encrypt` inject fixed bytes and
whose every other method is the real libsodium call. This is exactly the shape the
existing round-trip test already builds
(`packages/sync-client/src/push/roundtrip.test.ts:21-64`), so the generator reuses
that provider rather than inventing a second one. The provider seam exists in
production (`packages/sync-client/src/push/crypto-provider.ts:15-27`), so this is
still a production code path with a test-supplied entropy source, not a
reimplementation.

There is no third technique. Recording a generated nonce into the vector as an input
was considered and rejected: it makes the file reproducible only by the verifier and
not by the generator, which is precisely the carve-out that would exempt the most
important classes from the `vectors:check` gate. Every generator injects.

Fixed material, shared across every generator so a reader can correlate vectors:

| Name                    | Value                                                             | Purpose                                                       |
| ----------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------- |
| `SEED_A`                | `a0` repeated 32 times                                            | Ed25519 signer A, already in use (`gen-crypto-vectors.ts:46`) |
| `SEED_B`                | `5c` repeated 32 times                                            | X25519 secret B, already in use (`:47`)                       |
| `SEED_C`                | `3e` repeated 32 times                                            | new: Ed25519 signer B, for multi-signer cases                 |
| `VAULT_KEY`             | `vaultUnlockFlow.vaultKeyHex` from the existing file              | binds the new classes to the existing unlock vector           |
| `FILE_KEY`              | `fedcba98...` as already committed (`vaultUnlockFlow.fileKeyHex`) | same                                                          |
| `NONCE_24_A`            | `000102...1617`                                                   | data nonce, already in use (`:51`)                            |
| `NONCE_24_B`            | `NONCE_24_A` reversed                                             | key nonce, already in use (`:52`)                             |
| `NONCE_24_C`            | `ff` repeated 24 times                                            | new: second data nonce, for two-item cases                    |
| `DEVICE_A` / `DEVICE_B` | `device-a` / `device-b`                                           | clock keys, human readable on purpose                         |
| `NOTE_ID`               | `abc123def456`                                                    | a valid 12 character note id                                  |
| `JOURNAL_ID`            | `j2026-04-16`                                                     | a valid journal id                                            |

Every generator writes `JSON.stringify(v, null, 2) + '\n'` and every file carries a
`meta` block mirroring the existing one
(`packages/contracts/test-vectors/crypto-vectors.json`): `spec`, `sodiumVersion`,
`encoding`, and the production constants the class depends on, so a constant change
shows up as a vector diff.

Encoding convention, inherited from the existing file: **hex unless the field name
says otherwise**, and a field whose name ends `Base64` or `B64` is base64 with the
standard alphabet and padding.

## 3. Class: cryptographic primitives (exists)

**Status**: shipped. `packages/contracts/test-vectors/crypto-vectors.json`,
generated by `packages/contracts/scripts/gen-crypto-vectors.ts`, verified by
`packages/contracts/src/__tests__/crypto-vectors.test.ts`.

**Groups and counts, as committed**: `argon2id` 2, `xchacha20poly1305Ietf` 2,
`ed25519` 1 object, `kdfDeriveFromKey` 7, `generichash` 3, `auth` 1,
`scalarmult.base` 2, `scalarmult.shared` 2, `boxKeypair` 1 object,
plus the `vaultUnlockFlow` object covered in section 4.

**What the desktop test asserts**: ten cases
(`packages/contracts/src/__tests__/crypto-vectors.test.ts:98-258`). It pins the
production constants against `ARGON2_PARAMS` and `XCHACHA20_PARAMS`, recomputes
every primitive with Node libsodium, asserts `kdfDeriveFromKey` has exactly 7
entries, verifies signatures rather than only comparing them, verifies the MAC
rather than only comparing it, and asserts both ECDH directions agree. It never
regenerates.

**What the Rust test asserts**: the same, through `libsodium-sys-stable` with the
`dryoc` cross-check running every case a second time, plus the `deviceIdHex`
derivation.

**Three changes this feature must make, none of which touch the committed file.**
The file's bytes stay exactly as they are; two of these are assertions added to the
verifier and one is a new file:

1. **Import the KDF table instead of copying it. Verifier-only.** The generator hard
   codes the seven context and subkey-id pairs (`gen-crypto-vectors.ts:25-35`) with a
   comment saying it mirrors `apps/desktop/src/main/crypto/keys.ts:19`. That is a
   copy, so a change to one does not fail the other. The verifier asserts that the
   vector's context and id pairs equal the production map. No case is added and the
   file does not change.

2. **The BIP39 gap is real, and it is closed in `bip39-unlock.json`, not here.** The
   committed `vaultUnlockFlow` starts from a **password**
   (`vaultUnlockFlow.passwordUtf8`), but the production unlock path a phone must
   implement starts from a **24 word recovery phrase** and passes through
   `bip39.mnemonicToSeed`, which is PBKDF2-HMAC-SHA512 with 2048 iterations and the
   literal salt `mnemonic` (`apps/desktop/src/main/crypto/recovery.ts:11-13`). That
   entire step is uncovered. FR-019 and SC-003 depend on it, and it is the step a
   Rust implementation is most likely to get subtly wrong, for example by passing a
   BIP39 passphrase or by normalising differently. See section 4 for the new file's
   contents.

3. **Assert the `deviceId` derivation in the verifier** against the `ed25519` public
   key already in the file, so the Rust test has an obvious target:
   `deviceId = hex(crypto_generichash(16, ed25519PublicKey, null))`
   (`apps/desktop/src/main/crypto/keys.ts:81`). Again verifier-only; no new case.

**Count for this class**: 20, unchanged.

## 4. Class: vault unlock (exists, extended)

**Status**: shipped as the `vaultUnlockFlow` object.

**Generator**: `gen-crypto-vectors.ts:229-276`. Determinism by D1 throughout: fixed
password, fixed `kdfSalt`, fixed `fileKey`, fixed `keyNonce`, fixed `dataNonce`.

**Shape**: one object carrying `passwordUtf8`, `kdfSaltHex`, `argon2 {opsLimit,
memLimit}`, `masterKeyHex`, `keyVerifierBase64`, `vaultKeyHex`, `fileKeyHex`,
`keyNonceHex`, `encryptedKeyHex`, `dataNonceHex`, `encryptedDataHex`,
`plaintextMarkdownUtf8`, `plaintextSha256Hex`.

**Desktop assertions**: seven, walking the whole chain and ending at a SHA-256 of
the recovered plaintext (`crypto-vectors.test.ts:218-258`).

**Rust assertions**: identical, ending at the same digest.

**Extensions this feature requires, all of them in the new `bip39-unlock.json`.**
The committed `vaultUnlockFlow` object is not touched. The new file carries a
`bip39` group of 4 cases plus a `verifiers` group of 4:

`bip39`, 4 cases: a known 24 word English mnemonic with its expected 64 byte seed;
the same mnemonic with mixed case and doubled internal spaces, carrying the seed it
actually produces today so the normalisation behaviour is pinned rather than assumed;
a mnemonic with a deliberately invalid checksum and the expected validation result;
and a 12 word mnemonic, to pin that the product uses 24 and what a 12 word input
does.

`verifiers`, 4 cases:

| Case                    | Why                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `recoveryPhraseUnlock`  | The phrase path end to end: mnemonic to seed to master key to vault key to verifier. This is the path FR-019 ships and the existing case does not cover it.                                                                                                                                                                                                                                      |
| `accountKeyVerifier`    | Pin that the verifier is literally `base64(kdf(32, 4, 'memrykve', masterKey))` with no hash wrapper (`apps/desktop/src/main/crypto/keys.ts:110-117`), and that comparison is over the base64 **strings** re-encoded as UTF-8, not the decoded bytes (`recovery.ts:48-55`). A Rust implementation that compares decoded bytes still passes for correct input and fails to reject some wrong ones. |
| `localVaultKeyVerifier` | `base64(crypto_generichash(32, "memry/vault-key-verifier/v1/<vaultId>", vaultKey))` (`apps/desktop/src/main/crypto/vault-key-state.ts:14-26`), including the exact message string with the vault id appended.                                                                                                                                                                                    |
| `wrongPhrase`           | A phrase that is valid BIP39 but not this vault's, with the expected verifier mismatch, so the failure path is pinned too (FR-027).                                                                                                                                                                                                                                                              |

**Count target**: `crypto-vectors.json` keeps its 1 `vaultUnlockFlow` object;
`bip39-unlock.json` is 8 new cases, 4 plus 4.

## 5. Class: signed record envelope (new)

**File**: `record-envelope.json`.

**Generator**: `gen-protocol-vectors.ts`, calling **desktop's** `encryptItemForPush`
from `apps/desktop/src/main/sync/encrypt.ts:35-109` and `decryptRecordItem` from
`packages/sync-client/src/pull/record-decrypt.ts:42`. Desktop is the implementation
that wrote every byte in every live vault, so it is the one the vectors must come
from. `packages/sync-client/src/push/record-encrypt.ts:36` only claims parity with it
by comment.

**The verifier turns that comment into a test.** For every case in this file, the
desktop test asserts that `encryptRecordForPush` from
`packages/sync-client/src/push/record-encrypt.ts` produces bytes identical to the
committed `pushItem`, given the same injected material. Two implementations of the
same envelope exist in this repo; this is the only thing that keeps them the same.

**Determinism**: D2, applied at desktop's crypto boundary. The deterministic
`SyncCryptoProvider` described in section 2 is lifted from
`packages/sync-client/src/push/roundtrip.test.ts:21-64` into a shared
`test-vectors/deterministic-provider.ts` so generator and verifier use one
implementation. `generateFileKey` returns `FILE_KEY`; `encrypt` uses `NONCE_24_A`
for content and `NONCE_24_B` for the wrap; everything else is real libsodium. If
`encryptItemForPush` has no injectable seam today, adding one narrow test-only
parameter for the file key and the two nonces is part of A2, and is strictly better
than recording the random values into the file.

**JSON shape**, per case:

```json
{
  "name": "note create, compressible body, with clock",
  "input": {
    "id": "abc123def456",
    "type": "note",
    "operation": "create",
    "contentUtf8": "...",
    "vaultKeyHex": "...",
    "signingSeedHex": "...",
    "fileKeyHex": "...",
    "dataNonceHex": "...",
    "keyNonceHex": "...",
    "clock": { "device-a": 3 },
    "deletedAt": null
  },
  "expected": {
    "compressedHex": "...",
    "signaturePayloadCborHex": "...",
    "pushItem": {
      "id": "...",
      "type": "...",
      "operation": "...",
      "encryptedKey": "...",
      "keyNonce": "...",
      "encryptedData": "...",
      "dataNonce": "...",
      "signature": "...",
      "signerDeviceId": "...",
      "clock": { "device-a": 3 }
    },
    "sizeBytes": 1234
  }
}
```

`compressedHex` and `signaturePayloadCborHex` are intermediate values deliberately
exposed, because when a Rust implementation fails the final signature the useful
question is which of the three stages diverged. A vector that only carries the
final envelope forces a bisect by hand.

**Cases** (14):

| #   | Case                                                                                                                        | Pins                                                                                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `note` create, body over 64 bytes and compressible                                                                          | the `0x01` branch, the happy path                                                                                                                                           |
| 2   | `note` create, body under 64 bytes                                                                                          | the always-stored rule                                                                                                                                                      |
| 3   | `note` update, body over 64 bytes but incompressible (random bytes)                                                         | the "compression did not shrink" fallback to `0x00`                                                                                                                         |
| 4   | `note` delete with `deletedAt` set                                                                                          | `deletedAt` inside the signed CBOR                                                                                                                                          |
| 5   | `task` update with `clock` present                                                                                          | `metadata.clock`                                                                                                                                                            |
| 6   | `note` with `clock` and `stateVector`                                                                                       | both metadata keys, and that CBOR sorts `clock` before `stateVector` by length                                                                                              |
| 7   | `settings` update with **no** clock                                                                                         | the one clock-exempt type                                                                                                                                                   |
| 8   | `journal` update                                                                                                            | the type string, since journals are records for metadata and CRDT for body                                                                                                  |
| 9   | tamper: case 1's envelope with `clock` removed after signing                                                                | verification must fail; mirrors `roundtrip.test.ts:118-134`                                                                                                                 |
| 10  | tamper: case 1's envelope with one ciphertext byte flipped                                                                  | decrypt must fail                                                                                                                                                           |
| 11  | tamper: case 1's envelope signed by `SEED_A`, verified against `SEED_C`'s public key                                        | verification must fail                                                                                                                                                      |
| 12  | a payload whose encrypted size sits just under `SYNC_ITEM_MAX_ENCRYPT_BYTES / SYNC_ITEM_ENCRYPT_OVERHEAD` and one just over | the `ItemTooLargeError` boundary, `packages/sync-client/src/note-size.ts:16-31`                                                                                             |
| 13  | a vault-name envelope, encrypt and decrypt                                                                                  | `vault-name-crypto.ts`: the name is its own envelope with its own context, not a record payload, and a client that reuses the item envelope for it produces the wrong bytes |
| 14  | a vault-name envelope whose ciphertext is corrupted                                                                         | must return `null` rather than throwing (`vault-name-crypto.ts:25-37`), which is a different failure contract from every other case in this file                            |

Cases 9 through 11 carry `"expectFailure": "signature" | "decrypt"` instead of an
`expected` block. Case 14 carries `"expectNull": true`.

**Desktop assertions**: for each non-failure case, call desktop's
`encryptItemForPush` with the injected provider and assert every field of `pushItem`
matches; then call `encryptRecordForPush` from
`packages/sync-client/src/push/record-encrypt.ts` with the same material and assert it
produces the identical bytes; separately call `decryptRecordItem` on the committed
envelope and assert the plaintext equals `contentUtf8`. For each failure case, assert
the specified error type. The round-trip direction matters as much as the forward
one: a generator bug that is symmetric would otherwise pass.

**Rust assertions**: identical, both directions, plus an explicit assertion that
`signaturePayloadCborHex` matches before the signature is computed, so a CBOR
divergence is reported as a CBOR failure rather than a signature failure.

## 6. Class: packed CRDT update (new)

**File**: `crdt-update.json`.

**Generator**: `gen-protocol-vectors.ts`, calling **desktop's**
`apps/desktop/src/main/sync/crdt-encrypt.ts` and `decryptCrdtUpdatePacked`
(`packages/sync-client/src/pull/record-decrypt.ts:115`). Same reasoning as section 5:
desktop wrote the packets that exist.

**The verifier asserts parity** between desktop's packer and
`encryptCrdtUpdatePacked` in `packages/sync-client/src/push/crdt-encrypt.ts` for
every case, byte for byte.

**Determinism**: D2, same provider.

**JSON shape**, per case: inputs `noteId`, `updateHex` (the raw Yjs update bytes),
`vaultKeyHex`, `signingSeedHex`, `fileKeyHex`, `dataNonceHex`, `keyNonceHex`;
expected `packedHex` plus a decomposition block
`{ dataNonceHex, keyNonceHex, wrappedKeyHex, signatureHex, ciphertextHex }` and
`signedPayloadHex`. The decomposition is what turns an offset bug into a one-line
diagnosis.

**Cases** (8):

| #   | Case                                                                                         | Pins                                                                                                                                                          |
| --- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | a 512 byte Yjs update                                                                        | the compressible branch; 512 is chosen because the existing test already established that a short fixture never reaches deflate (`roundtrip.test.ts:158-159`) |
| 2   | a 40 byte update                                                                             | the stored branch                                                                                                                                             |
| 3   | a real Yjs update produced by `Y.encodeStateAsUpdate` over a small BlockNote-shaped document | that the transport does not inspect the bytes, and gives `yrs` something real                                                                                 |
| 4   | the same update for `JOURNAL_ID`                                                             | that a journal body uses the identical envelope, which is the concrete form of open question Q07.1                                                            |
| 5   | minimum length, exactly 161 bytes                                                            | the `HEADER_LEN + 1` guard (`record-decrypt.ts:122-124`)                                                                                                      |
| 6   | 160 bytes exactly                                                                            | must fail: "CRDT update too short"                                                                                                                            |
| 7   | case 1's packet decrypted as a different `noteId`                                            | must fail as a **signature** error, not an AEAD error, because the note id is authenticated (`roundtrip.test.ts:173-188`)                                     |
| 8   | case 1 with the last ciphertext byte flipped                                                 | must fail                                                                                                                                                     |

**Desktop assertions**: byte equality of `packedHex`, plus each field of the
decomposition sliced at the documented offsets, plus a round trip back to
`updateHex`, plus the failure cases.

**Rust assertions**: identical. Additionally, the Rust test asserts
`packedHex[96..160]` is the signature and `packedHex[160..]` is the ciphertext by
slicing at literal offsets, so a constant that drifts fails loudly rather than
shifting everything consistently.

## 7. Class: canonical CBOR (new)

**File**: `cbor-canonical.json`.

This class exists because the ordering rule is not what the field-order constant
looks like, and because a Rust CBOR crate's defaults differ from `cborg`'s in ways
that are invisible until a signature fails. See chapter 04 fact 7 of the protocol
outline.

**The citation, stated once and used everywhere.** The order `cborg` produces is
**length-first then bytewise**, which is RFC 8949 **§4.2.3**, "Length-First Map Key
Ordering". RFC 8949 §4.2.1, the core deterministic encoding, is **plain bytewise**
and is a different order. Every reference to length-first in the chapters, the
vectors and the code comments must cite §4.2.3. Three places in the tree cite §4.2.1
for length-first and are wrong: the comment at
`apps/desktop/src/main/crypto/cbor.test.ts:67`, and the stale ordering comments at
`packages/sync-client/src/pull/record-decrypt.ts:72`,
`packages/sync-client/src/push/record-encrypt.ts:74` and
`apps/desktop/src/main/sync/crdt-encrypt.ts:38`. Correcting all four is part of A2,
in the same change that lands this class.

**Generator**: `gen-protocol-vectors.ts`, calling `encodeCbor` from
`packages/contracts`-adjacent production code. Note there are two copies of this
function, `apps/desktop/src/main/crypto/cbor.ts:7-28` and
`packages/sync-client/src/pull/cbor.ts:9-30`, kept byte identical by comment. The
generator calls one and the verifier asserts both produce the same bytes for every
case, which turns that comment into a test.

**Determinism**: D1. Pure function, no randomness.

**JSON shape**, per case: `{ name, fieldOrderName, input, expectedHex,
expectedDecodedKeyOrder }` or `{ name, fieldOrderName, input, expectError }`.

**Cases** (14):

| #   | Case                                            | Pins                                                                                                                                                                                                                |
| --- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | a full `SYNC_ITEM` payload, all ten keys        | the real thing, and that the encoded order is `id, type, metadata, operation, cryptoVersion, ...` by length rather than the list order                                                                              |
| 2   | the same payload with keys inserted in reverse  | identical bytes; input order is irrelevant                                                                                                                                                                          |
| 3   | `{ aa: 1, z: 2 }` under a two-entry field order | **the length-first versus lexicographic disagreement**. Expected bytes are `a2 61 7a 02 61 61 01`, key order `z` then `aa`. A lexicographic encoder produces `a2 61 61 01 61 7a 02` and fails here and nowhere else |
| 4   | a nested `metadata` of `{ stateVector, clock }` | that nested maps are sorted **recursively**, giving `clock` then `stateVector`                                                                                                                                      |
| 5   | a nested `clock` of `{ d1: 1, aa: 2 }`          | equal-length keys sorted bytewise, giving `aa` then `d1`                                                                                                                                                            |
| 6   | a three-level nesting                           | that recursion does not stop at depth two                                                                                                                                                                           |
| 7   | integer `1`                                     | shortest form, `01`                                                                                                                                                                                                 |
| 8   | integer `1000000`                               | shortest form, `1a 000f4240`                                                                                                                                                                                        |
| 9   | integer `-1`                                    | `20`                                                                                                                                                                                                                |
| 10  | float `1.5`                                     | **float16 narrowing**, `f9 3e00`                                                                                                                                                                                    |
| 11  | float `0.1`                                     | float64 when narrowing is lossy, `fb 3fb999999999999a`                                                                                                                                                              |
| 12  | a `Uint8Array` value                            | major type 2, `43 010203`, not an array of integers                                                                                                                                                                 |
| 13  | `null` and `true` values                        | `f6`, `f5`, and that `null` is encoded while `undefined` is dropped                                                                                                                                                 |
| 14  | a payload with a key not in the field order     | must throw `CBOR encoding rejected: ...`                                                                                                                                                                            |

Cases 7 through 12 are scalars encoded as single-key maps so they exercise the same
entry point rather than a hypothetical scalar API.

**Desktop assertions**: `encodeCbor(input, CBOR_FIELD_ORDER[fieldOrderName])` equals
`expectedHex`; `decode(bytes)` yields `expectedDecodedKeyOrder`; the two
implementations of `encodeCbor` agree; case 14 throws with the documented message.

**Rust assertions**: the chosen CBOR crate, configured for canonical output, equals
`expectedHex` for every case. Case 3 is the one that will fail first on a crate whose
"canonical" setting means RFC 8949 §4.2.1 core deterministic (plain bytewise) rather
than §4.2.3 length-first, which is what this protocol uses. Pin the crate and the
setting in the Rust test's own comment.

**Note on whether any signed field can be non-integral**: today no. Every signed
numeric field is an integer by construction: `cryptoVersion` is the literal 1, every
clock tick is `z.number().int().nonnegative()`
(`packages/contracts/src/sync-api.ts:308`), and `deletedAt` on the push item is
`z.number().int().min(0)` (`:363`). But `SignaturePayloadV1Schema.deletedAt` is a
bare `z.number()` with no `.int()` (`packages/contracts/src/crypto.ts:214`). Cases 10
and 11 exist so that when someone does send a fractional value, the behaviour is
already pinned rather than discovered. This is recorded as Q04.7 in the protocol
outline.

## 8. Class: compression framing (new)

**File**: `compression.json`.

**Generator**: `gen-protocol-vectors.ts`, calling `compressPayload` and
`decompressPayload` from `packages/sync-client/src/compress.ts`.

**Determinism**: D1, with one caveat. `pako.deflate` output is deterministic for a
given input and library version, but it is not part of the protocol that it be a
particular byte sequence: any valid zlib stream that inflates to the right bytes is
conformant. So the vectors record both, and the assertions differ:

- `expectedFrameHex` is the exact `pako` output. The **desktop** test asserts
  equality against it, which is what detects a `pako` upgrade changing output.
- The **Rust** test asserts the weaker, correct property: that inflating
  `expectedFrameHex[1..]` yields the input, that the flag byte matches, and that
  its own compressor's output round-trips through `decompressPayload`. Requiring a
  Rust `flate2` to produce byte-identical output to `pako` would be a false
  requirement and would fail for a reason that does not matter.

The generator records the `pako` version in `meta`.

**JSON shape**: `{ name, inputHex, expectedFlag, expectedFrameHex,
expectedInflatedHex }`, or `{ name, frameHex, expectError }`.

**Cases** (9):

| #   | Case                                                                   | Pins                                                                                                                                                                                                 |
| --- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 63 bytes of highly compressible text                                   | flag `0x00`, stored, because the threshold is strict "under 64"                                                                                                                                      |
| 2   | 64 bytes of highly compressible text                                   | flag `0x01`, the first byte that is allowed to compress                                                                                                                                              |
| 3   | 4 KiB of repeated text                                                 | flag `0x01`, and that the payload begins `78 9c`                                                                                                                                                     |
| 4   | 4 KiB of cryptographically random bytes                                | flag `0x00`, because deflate does not shrink random data                                                                                                                                             |
| 5   | a payload where deflate output is exactly equal in length to the input | flag `0x00`, the `>=` boundary rather than `>`                                                                                                                                                       |
| 6   | empty input                                                            | returned as-is, no flag prepended on decompress of an empty buffer (`compress.ts:20`)                                                                                                                |
| 7   | a frame with flag `0x02`                                               | treated as **stored**, the payload returned verbatim; there is no unknown-flag rejection                                                                                                             |
| 8   | a valid `0x01` frame truncated to half its length                      | **must be a hard error**, `Failed to decompress payload: incomplete deflate stream`. This is the case that protects against a truncated body decoding as an empty content wipe (`compress.ts:26-44`) |
| 9   | a `0x01` frame whose payload is gzip rather than zlib                  | must fail, and exists purely to catch a Rust implementation that reached for `GzEncoder`                                                                                                             |

**Desktop assertions**: `compressPayload(input)` equals `expectedFrameHex` and
`decompressPayload(expectedFrameHex)` equals `inputHex`, plus the two error cases.

**Rust assertions**, stated as the property rather than as byte equality: for every
compressed case, `expectedFrameHex[1..]` **inflates under `flate2` to the input and
begins `78 9c`**; the flag byte matches; and the Rust compressor's own output
round-trips back through `decompressPayload`. Plus case 9, the gzip-framed payload,
which **must fail**, because it is the single case that catches an implementation
that reached for `GzEncoder`, and case 8, which must return an error rather than an
empty buffer.

## 9. Class: field merge (new)

**File**: `field-merge.json`.

This is the class FR-002 names, and it is the one where the specification currently
has no written source at all. The heuristics live only in
`packages/sync-client/src/field-merge.ts:102-125`.

**Generator**: `gen-protocol-vectors.ts`, calling `mergeFields` directly. Pure
function, no determinism problem at all. The generator's job is to enumerate cases
and record the real output, not to predict it: a generator that asserts what it
thinks the answer should be would encode the author's belief rather than the
implementation's behaviour.

**JSON shape**, per case:

```json
{
  "name": "tie broken by local offline tick",
  "syncableFields": "TASK",
  "localData": { "title": "phone title", "priority": 2 },
  "remoteData": { "title": "desktop title", "priority": 2 },
  "localFieldClocks": { "title": { "_offline": 1, "device-a": 2 }, "priority": { "device-a": 3 } },
  "remoteFieldClocks": { "title": { "device-a": 3 }, "priority": { "device-a": 3 } },
  "expected": {
    "merged": { "title": "phone title", "priority": 2 },
    "mergedFieldClocks": {
      "title": { "_offline": 1, "device-a": 3 },
      "priority": { "device-a": 3 }
    },
    "hadConflicts": false,
    "conflictedFields": [],
    "conflicts": []
  }
}
```

`syncableFields` names `TASK` or `PROJECT` so the verifier picks the right list;
the vector file also carries the two lists in `meta` so the Rust side can assert it
has the same 15 and 9 entries in the same order.

**Named cases, covering the clockTotal and `_offline` heuristics explicitly** (18):

| #   | Name                                             | What it pins                                                                                                                                                                                |
| --- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `remote-total-greater`                           | rule 1, remote wins outright                                                                                                                                                                |
| 2   | `local-total-greater`                            | rule 2, local wins outright                                                                                                                                                                 |
| 3   | `totals-equal-values-equal`                      | rule 4 default, remote wins, no conflict because values match                                                                                                                               |
| 4   | `totals-equal-values-differ-no-offline`          | rule 4 default, **remote wins a plain tie**                                                                                                                                                 |
| 5   | `totals-equal-local-has-offline`                 | rule 3, local wins                                                                                                                                                                          |
| 6   | `totals-equal-remote-has-offline`                | **the asymmetry**: remote already wins by rule 4, so this looks the same as case 4. Named separately because it is the case an implementer will assume is symmetric                         |
| 7   | `totals-equal-both-have-offline`                 | rule 3 does not fire, remote wins                                                                                                                                                           |
| 8   | `totals-equal-local-offline-but-values-equal`    | rule 3 requires `valsDiffer`, so remote wins                                                                                                                                                |
| 9   | `clock-total-beats-causality`                    | local clock is `{a:5}`, remote is `{b:2, c:2}`; local total 5 beats remote total 4 even though the clocks are concurrent. **This is the case that shows `clockTotal` is not a causal rule** |
| 10  | `concurrent-equal-totals-values-differ`          | the only shape that reports a conflict: all three conditions hold                                                                                                                           |
| 11  | `concurrent-unequal-totals-values-differ`        | **concurrent but silently resolved**, `hadConflicts` false. The lost-edit case                                                                                                              |
| 12  | `missing-local-field-clock`                      | absent clock defaults to `{}`, total 0                                                                                                                                                      |
| 13  | `missing-both-field-clocks`                      | both `{}`, tie, remote wins                                                                                                                                                                 |
| 14  | `field-absent-from-syncable-list`                | a field present in the data but not in the list is not merged at all and not present in `merged`                                                                                            |
| 15  | `null-versus-undefined`                          | `JSON.stringify(null) !== JSON.stringify(undefined)`, so these count as differing                                                                                                           |
| 16  | `object-values-same-content-different-key-order` | **`JSON.stringify` equality is key-order sensitive**, so `{a:1,b:2}` and `{b:2,a:1}` count as differing. The single likeliest Rust divergence                                               |
| 17  | `number-formatting`                              | `1` versus `1.0` stringify identically; `0.1 + 0.2` does not equal `0.3`                                                                                                                    |
| 18  | `project-fields`                                 | one case over `PROJECT_SYNCABLE_FIELDS` so the second list is exercised                                                                                                                     |

Plus a second group in the same file, `clockAlgebra`, 8 cases over
`compare`, `merge` and `increment` from `packages/sync-client/src/vector-clock.ts`:
equal, before, after, concurrent, concurrent-detected-early, merge commutativity,
increment from absent, and a clock containing `_offline` compared against one that
does not.

Plus a third group, `offlineRebind`, 4 cases over
`rebindOfflineClockData` (`packages/sync-client/src/offline-clock.ts:68`): a clock
with only `_offline`, a clock with `_offline` and the target device already present
(the tick counts **add**), a clock with no `_offline` (unchanged), and field clocks
where only some fields carry `_offline`.

**Count target**: 18 plus 8 plus 4 equals 30.

**Desktop assertions**: `mergeFields` output deep-equals `expected`, field by field,
including `conflictedFields` as an ordered array (the order is the order of
`syncableFields`, which is itself a fact worth pinning).

**Rust assertions**: identical. FR-002 requires that two implementations produce the
same winner **and the same conflict set**, so both halves are asserted; a Rust
implementation that gets every winner right and reports conflicts more eagerly
fails, correctly.

## 10. Class: MPAK pack container (new)

**File**: `pack-container.json`.

**Generator**: `gen-protocol-vectors.ts`. The pack **writer** lives server side and is
not in `packages/contracts`, which only ships the reader
(`packages/contracts/src/pack-format.ts:10-14`).

**These are reader-only vectors, and the server's writer is not imported.**
`packages/contracts` must not depend on `apps/sync-server`; making the exception for a
script inside the package would put the dependency in the package's own tree and
weaken a boundary that exists for a reason. So the generator hand-assembles the bytes
and the verifier asserts that `parsePack` accepts them and returns the expected
entries. That proves the reader, which is the only half a Rust client needs: the
phone is never a pack writer, and the writer stays covered by the server's own tests.

**Determinism**: D1. Payload bytes are fixed, digests are SHA-256 of them.

**JSON shape**: `{ name, packHex, expected: { version, entries: [...] } }` or
`{ name, packHex, expectError }`. `packHex` for the largest case will be a few
kilobytes of hex, which is acceptable; if it grows past that, switch to base64 and
say so in `meta.encoding`.

**Cases** (10):

| #   | Case                                                                  | Pins                                                                                                                                 |
| --- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | one `record` entry                                                    | the minimal valid pack, header, one index record, footer                                                                             |
| 2   | three entries, one of each kind                                       | `PackKindCode` 0, 1, 2 and mixed `sortKey` semantics                                                                                 |
| 3   | a `crdt_snapshot` entry with `{sequenceNum, revision}` meta           | the JSON meta field and the freshness token                                                                                          |
| 4   | an entry with an empty meta field                                     | `metaLen` 0 and no `meta` key on the decoded entry                                                                                   |
| 5   | a multi-byte UTF-8 identity, for example a folder path with non-ASCII | that `idLen` is **bytes**, not characters                                                                                            |
| 6   | header magic corrupted                                                | reject                                                                                                                               |
| 7   | header version set to 2                                               | reject with `unsupported pack version 2`                                                                                             |
| 8   | footer `payloadSha256` corrupted                                      | reject with `pack payload checksum mismatch`                                                                                         |
| 9   | one entry's `sha256` corrupted, payload digest still valid            | reject with `pack entry checksum mismatch: <id>`, proving per-entry verification is not skipped when the whole-payload digest passes |
| 10  | `entryCount` in the footer set above `PACK_MAX_ENTRIES`               | reject, proving the bound is structural                                                                                              |

**Desktop assertions**: `parsePack(bytes)` returns `integrityVerified: true` and the
expected entry array for the good cases; throws the documented message for each bad
case; `readFooter` on the tail slice alone works, since a streaming reader passes
only the tail (`pack-format.ts:206-212`).

**Rust assertions**: the same, with explicit big-endian integer decoding and
explicit `offset` interpretation as relative to `PACK_HEADER_SIZE`, which is the
off-by-eight a reader gets wrong first.

## 11. Class: markdown round-trip corpus (new)

**File**: `markdown-roundtrip/cases.json` and `markdown-roundtrip/fuzz-families.json`.

**The corpus already exists in code** and this class should extend it rather than
start over. `packages/editor-schema/src/conformance.ts` exports 80
`ROUNDTRIP_CASES` plus 5 `FUZZ_FAMILIES` and a seeded PRNG, and two existing test
files consume it: the renderer pipeline
(`apps/desktop/src/renderer/src/components/note/content-area/roundtrip-conformance.test.ts`)
and the main and CRDT pipeline
(`apps/desktop/src/main/sync/blocknote-converter.roundtrip.test.ts`), both fuzzing
48 seeded cases per family at seed `0x1848`. The corpus bytes are generated by
calling the production serializers directly
(`serializeLinkMentionToken`, `serializeCalloutBlock`, `serializeToggleBlock`,
`serializeDateMentionToken`), so they already satisfy the "comes from production
code" rule.

**Generator**: `gen-protocol-vectors.ts` imports `ROUNDTRIP_CASES` and serialises it
to JSON, adding a digest per case. It does not invent cases; it exports the ones
that exist so a Rust or Swift consumer can read them without importing TypeScript.

**JSON shape**:

```json
{
  "meta": {
    "source": "packages/editor-schema/src/conformance.ts",
    "caseCount": 80,
    "fuzzSeed": "0x1848"
  },
  "cases": [
    { "name": "...", "markdown": "...", "canonical": null, "pending": null, "sha256": "..." }
  ],
  "fuzzFamilies": [{ "name": "link mention urls", "casesPerFamily": 48, "pending": null }]
}
```

**What the desktop suite asserts**: unchanged, the two existing round-trip tests.
Add one assertion: that `markdown-roundtrip/cases.json` is in sync with `ROUNDTRIP_CASES`,
so the exported file cannot drift from the in-code corpus. That is the FR-008 gate
for this class.

**What the Rust suite asserts: preservation only, and that is now a decision rather
than a recommendation.** Q12.2 is answered: the Rust core never converts markdown to
a Y.Doc and never serialises one back, because the WebView bundle owns both
directions. So the core's only obligation here is **byte preservation**: read a body,
write it back unchanged, and the digest matches. One assertion per case, 80 cases,
plus the 5 fuzz families at the same seed. No BlockNote block model in Rust, no
markdown grammar in Rust, and no parse-and-serialise round trip on this side.

Add four cases the existing corpus does not cover, because they are about the storage
layer rather than the editor:

| Case                                     | Why                                                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| a file with a BOM                        | `splitFrontmatterBlock` includes it in the block (`packages/app-core/src/markdown.ts:22`, `:34`) |
| a file with CRLF line endings throughout | `eol` detection and re-application (`:60`)                                                       |
| a file with an unclosed `---` block      | not frontmatter; the whole file is body (`:39`)                                                  |
| a file with no trailing newline          | `hadTrailingNewline` (`:61`)                                                                     |

**Count target**: 80 existing plus 4 equals 84 cases, plus 5 fuzz families at 48
seeded cases each.

### 11.1 Sub-class: out-of-band encodings (new)

A second group in `markdown-roundtrip/cases.json`, 5 cases, one per encoding that
lives outside the `prosemirror` fragment or outside plain markdown: inline colours,
block markers, suggestion marks (`criticMarkupMarks`), link references
(`linkReferenceDefinitions` and `linkReferenceUsages`), and the `markdownSource`
root. Each case is a Y update that carries the encoding.

**What the Rust suite asserts**: apply the update to a fresh `yrs` document, encode
the document back out, and assert the encoding survives. The failure this catches is
a core that replays only `prosemirror` and silently drops the other roots, which
looks like a working client right up until a desktop user loses their suggestion
marks. Protocol outline Q12.5 decides which roots are required rather than optional;
these cases are how the answer becomes a test.

### 11.2 Class: text extraction (new)

**File**: `text-extract.json`.

**Generator**: `gen-protocol-vectors.ts`, loading real desktop Y.Docs from a
staging vault fixture and emitting, per case, the Y update bytes as input and the
extracted text as expected output. The extraction it calls is the TypeScript
reference `extract_text` port in `packages/contracts/scripts/extract-text.ts`, which
walks the same fragment the Rust `extract_text` walks, so the vector is the contract
between them. That same port is what the SC-010 cross-shell digest is computed from
on the desktop side (`packages/contracts/scripts/digest.ts`, protocol outline chapter
12 fact 11), so a digest comparison can only fail on content, never on a second
extractor nobody pinned.

**JSON shape**, per case: `{ name, updateHex, expectedText }`.

**Cases** (12): a plain paragraph document; nested headings at every level; an
ordered list; an unordered list; a nested list; a table; a callout; a toggle; a code
block; a document with inline marks (bold, link, colour); an empty document; and a
document with a non-ASCII body so the walker's character handling is pinned.

**What is deliberately not claimed**: this is not markdown. Headings and list
markers are kept because search and previews read better with them; everything else
is dropped. A case whose `expectedText` looks like markdown is a coincidence of the
input, not a contract.

**Rust assertions**: `extract_text(doc)` after `apply_update(updateHex)` equals
`expectedText`, byte for byte, for every case. This is also the assertion gate G4
runs across a whole real vault.

  `totals-equal-local-offline-zero-tick` pins that the `_offline` tie-break is a

  and `float-accumulation` pins the other half of the number-formatting case;
- `markdown-roundtrip/cases.json` carries **90**, not 89: a sixth out-of-band
  case carrying a **foreign root no client knows**, without which the class only
  proves that roots someone remembered to list survive.

`packages/contracts/test-vectors/README.md` carries the same reconciliation next
to the files, along with the two other points where the built classes differ
from this design record and why.

SC-001 reads "100% of the committed conformance vectors pass in the second
implementation, byte for byte, before any shell work begins". That is this table.

**The FR-008 gate**, concretely:

1. `pnpm --filter @memry/contracts vectors:check` regenerates every class into a
   temporary directory and diffs against the committed files. Any difference fails.
   No class is exempt. This catches a constant change, a `pako` upgrade, a `cborg`
   upgrade, and a field-order edit.
2. The per-class verifiers in `packages/contracts/src/__tests__/` run in the desktop
   suite as they do today and catch an implementation change that the generator
   would not notice.
3. The protocol chapters cite the same constants the vectors pin. A chapter whose
   fact table disagrees with a vector is a review failure, and the chapter's own
   constant table should be asserted against the imported constants in the same test
   file, which turns the citation into a check.

Both 1 and 2 are required. A generator-only gate passes when the implementation and
the generator drift together; a verifier-only gate passes when a committed vector is
stale in a way the implementation happens to still satisfy.
